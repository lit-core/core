# Ahead-of-time Lit template compilation

`@lit-core/html-aot` is a compile-time transform that pre-compiles Lit `html` and `svg` tagged template literals into static `CompiledTemplateResult` descriptors.

---

## The runtime prepare phase in standard Lit

In standard Lit applications, when a tagged template literal `html\`<button class="${type}">\${label}</button>\`` executes for the first time:
1. Lit extracts the static strings array and dynamic expression markers.
2. The browser creates an HTML `<template>` element and sets `innerHTML`.
3. Lit walks the DOM tree of the prepared template to find part locations (attributes, child nodes, text bindings).
4. Lit stores these part offsets into a cached `Template` record.

While Lit caches these prepared templates in memory, the initial preparation cost occurs on the main thread during first render, introducing render latency.

---

## Ahead-of-time compilation mechanics

`@lit-core/html-aot` shifts template parsing and part preparation from runtime to build time:

1. **Static HTML parsing**:
   Parses the template literal using `parse5` during bundling.
2. **Part index computation**:
   Computes exact child node paths, attribute binding offsets, and event handler indices ahead of time.
3. **Compiled template descriptor generation**:
   Replaces the runtime `html\`...\`` tagged template call with a lightweight static descriptor conforming to Lit's compiled template contract:
   ```javascript
   // Output generated by html-aot
   export const template = {
     ['_$litType$']: 1,
     h: '<h1>hello</h1>',
     parts: [/* pre-computed byte offsets */]
   };
   ```

At runtime in the browser, Lit bypasses `innerHTML` parsing and tree-walking entirely, proceeding directly to DOM cloning and part binding.

---

## Trade-offs and performance characteristics

- **First render speedup**: Delivers +35% to +38% faster initial render times.
- **Bundle size impact**: Because part metadata descriptors are stored in JavaScript, compiled descriptors add ~1.5% to ~3.5% raw bundle bytes. For applications prioritizing fastest initial render latency, this trade-off is often desirable.
